# PR-3: บัตรจองร่วมทุกบริการ

- ฐานล่าสุด: `372e405` (PR #88 merge แล้ว), branch `feat/booking-cassette-pass`
- แยกตัวบัตรและ dialog QR เป็น partial เดียว คงส่วนจัดการ/เพื่อนร่วมห้อง/ledger ที่พักในหน้าผู้รับผิดชอบเดิม
- สร้าง context ใน services ตรวจ `can_view_details` ก่อนคืนข้อมูล QR ใช้เฉพาะ URL รายละเอียดจาก `PUBLIC_BASE_URL` ที่เป็น origin ถูกต้อง ไม่ใช้ host/header จากคำขอ
- ถ้า URL กลางว่างหรือผิดรูป แสดงบัตรที่อ่านได้และข้อความไทยว่า QR ยังไม่พร้อม โดยไม่สร้าง URL สมมติ
- บัตรห้องใช้สัดส่วนเวลาคาบ 0–1; ที่พักคงจำนวนคืนและรูปเดิม; JS รองรับทั้งสองและหยุด reels เมื่อ reduced-motion
- จองห้องสำเร็จไปบัตร (รวมรออนุมัติ), คง draft/error/series และขั้นตอนสาธารณะที่พักเดิม
- เพิ่มลิงก์บัตรในรายการ/รายละเอียด และปุ่มปฏิทิน คัดลอกลิงก์ จองอีกครั้งในบริการเดิม
- ตรวจสิทธิ์เชิงลบ ความคืบหน้า URL/QR ไม่มีข้อมูลส่วนตัว บัตรเดิมและการนำทาง แล้วรัน targeted/full pytest, check, migration drift, Node และ diff check
- Parent ตรวจเบราว์เซอร์จริงและทำ release; งานนี้ไม่เปลี่ยน schema/Cloud/ข้อมูล production

ข้อสงสัย: public lodging request ใช้หน้าสถานะที่มี token เดิมตามขอบเขต runbook; ไม่เปลี่ยนเป็นบัตร booking ที่ต้อง login ใน PR นี้

ข้อสงสัย: ผู้รักษาการแทนผู้อนุมัติและผู้อนุมัติข้อมูลอ่อนไหวอาจเห็น detail ด้วย `can_decide` เดิม แต่บัตรใช้ `can_view_details` ตาม runbook เท่านั้น จึงไม่ขยายสิทธิ์และไม่แสดงปุ่มบัตรให้กลุ่มนี้
