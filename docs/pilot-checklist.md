# Pilot Operation & Acceptance Checklist (B3)

ใช้คู่กับ `docs/deploy-guide.md` — เอกสารนี้ตอบ 3 คำถาม: **เปิด pilot ได้เมื่อไหร่ · ระหว่าง pilot ทำอะไรทุกวัน · ปิด pilot ว่า "ผ่าน" ได้เมื่อไหร่**

Pilot = ใช้จริงในเครือข่ายภายในหน่วย 1 เดือน กับผู้ใช้ 30–50 คน ห้อง 8 ห้อง

---

## 1. ก่อนประกาศเปิด pilot

- [ ] ตรวจรับติดตั้งครบทุกข้อ (deploy-guide หมวด 10)
- [ ] ผู้อนุมัติจริงของทุกห้องถูกตั้งในระบบ และแต่ละคน login ได้แล้ว
- [ ] ห้องประชุมผู้บังคับบัญชา (MTG-CO): หน่วยที่มีสิทธิ์จองตรงตามคำสั่ง ผบ.รร. (ประเด็นคงค้าง O4 ของ SRS)
- [ ] กำหนดผู้ดูแลระบบประจำ 1 คน + สำรอง 1 คน (ถือรหัสซองผนึก, ทำกิจวัตรเช้า)
- [ ] กำหนดช่องทางรับปัญหา 1 ช่องทางที่คนของหน่วยใช้จริง (สมุดหน้าห้องธุรการ / Google Form / กลุ่มไลน์ธุรการ) และติดประกาศไว้ที่หน้า login ของเครื่องประชาสัมพันธ์
- [ ] ประกาศ **ข้อจำกัดของ pilot** ให้ผู้ใช้ทราบล่วงหน้า (ติดบอร์ด/เวียนหนังสือ):
  - ไม่มีแจ้งเตือนทาง LINE — ดูกระดิ่งในระบบ
  - เข้าได้เฉพาะเครือข่ายภายในหน่วย ไม่ได้จากบ้าน/มือถือนอกหน่วย
  - ลืมรหัสผ่าน → ติดต่อผู้ดูแลระบบ (ยังกู้เองไม่ได้)
  - ยังพิมพ์แบบฟอร์ม/หนังสือราชการจากระบบไม่ได้
  - ไม่มี 2FA (ใช้ใน LAN เท่านั้นตามความเสี่ยงที่ยอมรับ)

## 2. กิจวัตรระหว่าง pilot

### ทุกเช้า (ผู้ดูแล ~5 นาที) — เช็ก backup ต้องครบ 3 อย่าง ห้ามดูแค่ log

- [ ] Task Scheduler → งาน SIGROOM Backup → **Last Run Result = `0x0`**
- [ ] โฟลเดอร์ backup มีไฟล์ `sigroom-*.dump` **timestamp เมื่อวาน 19:00**
- [ ] `backup-log.txt` บรรทัดล่าสุดเป็น `SUCCESS`

> เหตุที่ต้อง 3 อย่าง: ถ้าแชร์เครือข่ายล่มหรือ path พังก่อนสคริปต์เริ่มเขียน log จะ**ไม่มี**บรรทัด FAILED ใน log — ดูแค่ log จึงหลงคิดว่าปกติได้

- [ ] เปิดหน้าแรก SIGROOM หนึ่งครั้ง: ระบบขึ้น, คิวอนุมัติไม่มีรายการค้างผิดปกติ (ใกล้หมด SLA แต่ผู้อนุมัติไม่รู้ตัว → ทวงด้วยวาจา)
- [ ] มีปัญหาแจ้งเข้ามา → ลงตารางบันทึกข้อบกพร่อง (หมวด 4)

### ทุกศุกร์ (~15 นาที)

- [ ] `/reports/` → export CSV รายงานอัตราการใช้ห้อง เก็บเข้าโฟลเดอร์ `pilot-evidence\สัปดาห์-N\`
- [ ] ไล่ตารางข้อบกพร่อง: อะไรตอบแล้ว/ค้าง แจ้งกลับผู้แจ้ง

### รายเดือน (1 ครั้ง ช่วงเย็นที่ระบบว่าง ~30 นาที)

ทดสอบกู้คืนด้วยขั้นตอนสลับบัญชีชั่วคราว (เพราะ `sigroom_app` สร้าง/ลบฐานทดสอบไม่ได้ — โดยตั้งใจ)
**ต้องหยุดการเขียนก่อนและ backup สดทันทีก่อน restore** ด้วยเหตุผล 2 ข้อ: (ก) งาน Jobs ที่รันทุก 5 นาทีอาจอ่าน `.env` ตอนที่เป็น postgres ชั่วคราว (ข) restore-test เทียบจำนวน Booking ใน dump กับฐานจริง **ณ ปัจจุบัน** — ถ้ามีคนจองหลัง backup ล่าสุด ผลจะ "ไม่ผ่าน" ทั้งที่การกู้คืนสมบูรณ์

แจ้งผู้ใช้ล่วงหน้าว่าระบบปิดปรับปรุงช่วงนี้ แล้วทำตามลำดับ (สำคัญ: **Disable อย่างเดียวไม่พอ** — Disable แค่ห้ามรอบถัดไป ไม่ได้หยุดตัวที่กำลังรันอยู่):

1. Task Scheduler → คลิกขวางาน **SIGROOM Jobs** → **Disable** (กันรอบใหม่เริ่ม)
2. ถ้าคอลัมน์ Status ของ Jobs เป็น Running อยู่ ให้รอจนจบ (ไม่เกิน 1–2 นาที)
3. คลิกขวางาน **SIGROOM Server** → **Disable** แล้วคลิกขวาอีกครั้ง → **End** เพื่อหยุด instance ที่กำลังรัน
4. ตรวจว่าหยุดจริง: Status ของ Server ไม่เป็น Running และเปิด `http://localhost:8000` ต้อง**เข้าไม่ได้** — จากจุดนี้ไม่มีใครเขียนข้อมูลได้แล้ว
5. แก้ `.env`: `DB_USER=postgres` + รหัส postgres
6. `powershell -ExecutionPolicy Bypass -File scripts\backup.ps1` (backup สด ให้ dump ล่าสุดตรงกับฐาน ณ ตอนนี้)
7. `powershell -ExecutionPolicy Bypass -File scripts\restore-test.ps1` ทันที → ต้อง "ผ่าน"
8. คืน `.env` เป็น `sigroom_app`
9. Task Scheduler → **Enable** งาน SIGROOM Jobs และ SIGROOM Server
10. คลิกขวางาน Server → **Run** แล้วเปิดหน้าเว็บตรวจว่ากลับมาปกติ ถ่ายภาพผลข้อ 7 เก็บใน `pilot-evidence\`
11. สำรอง**ตัวโค้ด**ไปที่เดียวกับ dump (นโยบายหน่วย: ไม่ใช้คลาวด์ — ใช้ git bundle แทน):
   ```powershell
   cd C:\sigroom
   git bundle create \\SERVER-BACKUP\sigroom\sigroom-code.bundle main
   ```
   ทับไฟล์เดิมได้เลย — bundle เก็บประวัติ git ทั้งหมด กู้คืนด้วย `git clone sigroom-code.bundle`

> **ห้าม**แก้ปัญหาด้วยการเพิ่มสิทธิ์ CREATEDB ให้ `sigroom_app` เด็ดขาด

## 3. Mapping เกณฑ์รับมอบ SRS §15.2 (ครบทั้ง 17 ข้อ — โปร่งใสว่าข้อไหนตรวจตอนไหน)

สถานะ: ✅ ผ่านแล้วตอนติดตั้ง · 🔄 ตรวจระหว่าง/ท้าย pilot · ⏭ **Deferred by pilot scope** — เกณฑ์ SRS ยังคงบังคับอยู่ ไม่ได้ถูกยกเว้น เพียงเลื่อนการตรวจไปหลัง pilot/ก่อนเปิดอินเทอร์เน็ต/ก่อนขยายทั้งโรงเรียน ตามขอบเขตที่ pilot รอบนี้ตั้งใจไม่มี (LINE, Internet, ผู้ใช้จำนวนมาก)

> การแยกนี้สำคัญ: **"ผ่าน pilot" ≠ "ผ่าน SRS §15.2 เต็ม"** — pilot ผ่านได้เมื่อข้อ 🔄 ครบ ส่วนการรับมอบระยะที่ 1 เต็มรูปแบบต้องเก็บข้อ ⏭ ให้ครบก่อน

|---|---|---|---|
| 1 | ไม่มีการจองซ้อนทับตลอด pilot (ตรวจจากฐานข้อมูล) | 🔄 ท้าย pilot | รัน SQL ตรวจช่วงเวลาซ้อนของ BookingResource (คำสั่งในหมวด 5) ต้องได้ 0 แถว |
| 2 | ทุกคำขอได้ผลภายในเส้นตายหรือหมดอายุถูกต้อง ไม่มีคำขอค้างไร้สถานะ | 🔄 ท้าย pilot | Admin → Bookings กรองสถานะ pending ที่เลยวันใช้งาน ต้องเป็น 0 (run_jobs จัดการหมดอายุ) |
| 3 | ผู้อนุมัติลา → ผู้รักษาการอนุมัติได้ + log แสดง on_behalf_of | 🔄 ระหว่าง pilot | จัดสถานการณ์จริง 1 ครั้ง: ตั้ง delegation → รักษาการอนุมัติ → **Admin → Approvals** ดูว่า `acted_by` = ผู้รักษาการ และ `on_behalf_of` = ผู้อนุมัติหลัก · Audit log ใช้ยืนยันแค่ว่ามีเหตุการณ์อนุมัติเกิดขึ้น |
| 4 | บังคับย้าย (preemption) อย่างน้อย 2 สถานการณ์ ครบ FR-25–30 และช่วงเดิมว่างทันที | 🔄 ระหว่าง pilot | สถานการณ์ ก: ห้องทดแทนที่ผู้สั่งมีสิทธิ์ · ข: ห้องทดแทนต่างเจ้าของ — นัดทำกับผู้มีสิทธิ์สั่ง และหลังย้ายแต่ละครั้งให้**ทดลองจองช่วงเวลาเดิมของห้องเดิมทันที ต้องจองได้จริง** ไม่ใช่แค่ทำ preemption สำเร็จ |

| 6 | คำขอเร่งด่วนล่วงหน้า 30 ชม. → ผู้อนุมัติสำรองดำเนินการได้ (FR-23) | 🔄 ระหว่าง pilot | จองจริงล่วงหน้า**ประมาณ 30 ชม.** 1 ครั้ง (ตรงเกณฑ์ SRS — มีเทสยืนยันที่ 30 ชม. พอดี) ธง "เร่งด่วน" ต้องขึ้น และผู้อนุมัติ**สำรองกดอนุมัติ/ปฏิเสธได้ทันทีจริง** ไม่ใช่แค่เห็นคิว |

| 9 | ผู้ใช้ทั่วไปไม่เห็นชื่อกิจกรรม visibility จำกัด (ทดสอบข้ามหน่วย) | 🔄 ระหว่าง pilot | สร้างการจอง "จำกัด" แล้ว login บัญชีต่างหน่วยดู ปฏิทิน/บอร์ดต้องขึ้น "ไม่ว่าง" |

| 15 | architecture review + เอกสาร C4/ER/sequence/OpenAPI/ADR ตรงระบบ | ⏭ Deferred | เอกสารสถาปัตยกรรมเต็มชุดยังค้าง (มี build-plan + ADR บางส่วน) — ทำก่อนรับมอบเต็ม |
| 16 | Core Web Vitals + load test p75/p95 | ⏭ Deferred | ผู้ใช้ 30–50 คนใน LAN ยังไม่ถึงระดับที่ load test มีความหมาย — ทำก่อนขยายทั้งโรงเรียน |
| 17 | CI + quality gate + สาธิต deployment/rollback | ⏭ Deferred | ตอนนี้ใช้ pytest ก่อน commit + คู่มืออัปเดตเวอร์ชันใน deploy-guide — CI เต็มรูปแบบตั้งเมื่อมี repo กลาง |

**สรุปเกณฑ์ปิด pilot ว่า "ผ่าน" (operational acceptance):** ข้อ 1–9, 11 ครบทุกข้อ + ส่วน satisfaction ≥ 3.5/5 ของข้อ 14
**งานค้างสู่การรับมอบ SRS §15.2 เต็ม:** ข้อ 10, 12, 13, 15, 16, 17 ทั้งข้อ + ส่วน SUS ≥ 75 ของข้อ 14 — บันทึกเป็นแผนหลัง pilot ไม่นับว่าผ่าน

## 5. SQL ตรวจจองซ้อนท้าย pilot (เกณฑ์ข้อ 1)

รันด้วย psql (บัญชีใดก็ได้ที่อ่านได้):

```sql
SELECT a.booking_id AS จองที่1, b.booking_id AS จองที่2, a.resource_id
FROM bookings_bookingresource a
JOIN bookings_bookingresource b
  ON a.resource_id = b.resource_id
  AND a.booking_id <> b.booking_id
  AND a.id < b.id
  AND a.hold && b.hold
WHERE a.released_at IS NULL AND b.released_at IS NULL;
```

ต้องได้ **0 แถว** — และตามหลักแล้วเป็นไปไม่ได้ที่จะมี เพราะ constraint `excl_overlapping_holds` กันไว้ที่ฐานข้อมูล การรันนี้คือการพิสูจน์ซ้ำเพื่อเก็บหลักฐานรับมอบ

## 6. แบบสอบถามท้ายเดือน (แจกทุกผู้ใช้ ตอบ 1–5: 1 = ไม่เห็นด้วยอย่างยิ่ง … 5 = เห็นด้วยอย่างยิ่ง)

1. ฉันหาห้องว่างและจองได้ด้วยตัวเองโดยไม่ต้องถามใคร
2. สถานะคำขอของฉัน (รอ/อนุมัติ/ปฏิเสธ) ชัดเจนตลอดเวลา
3. ระบบเร็วพอสำหรับงานประจำวัน
4. หน้าจอบนมือถือ/แท็บเล็ตใช้งานได้จริง
5. เทียบกับวิธีเดิม (สมุด/โทรจอง) ระบบนี้ดีกว่า
6. (ผู้อนุมัติ) คิวอนุมัติช่วยให้ตัดสินใจได้เร็วและไม่มีตกหล่น
7. ข้อความปลายเปิด: อะไรที่อยากให้แก้เป็นอันดับแรก

**เกณฑ์ผ่าน: ค่าเฉลี่ยข้อ 1–6 ≥ 3.5** · เก็บผลดิบไว้ใน `pilot-evidence\`
