## นิยามที่ใช้ทั้งเอกสาร (ตัดปัญหาตีความ)

- **จุดเริ่มนับคลิก:** หลัง login สำเร็จและอยู่ที่หน้าแรกแล้ว โดยบัญชีผู้ใช้มีข้อมูลครบ
  (มีเบอร์โทรในโปรไฟล์) — การ login และการเปลี่ยนรหัสครั้งแรก **ไม่นับ** ทั้งคลิกและเวลา
- **"จองสำเร็จ" =** ระบบตอบรับคำขอแล้ว: ห้องนโยบาย AUTO ได้สถานะ **อนุมัติแล้วทันที** ·
  ห้องนโยบาย REQUIRED ได้สถานะ **รออนุมัติ** (เส้นทางฝั่งผู้ขอจบแล้ว — การรอผู้อนุมัติไม่นับเป็นความช้าของ UI)
  หน้ายืนยันต้องบอกผู้ใช้ชัดว่าได้แบบไหน
- **การกรอกข้อความไม่นับเป็นคลิก** แต่นับรวมในเวลาทดสอบ 2 นาที

## กติกา workflow (สืบทอดจากแผน V6 ข้อ 0 ทั้งหมด — สรุปซ้ำเฉพาะที่ต้องจำ)

1. Branch `feat/lodging-v5-2` คือ production (Cloud Build auto-deploy) — **ห้าม push ตรงเด็ดขาด**
2. พัฒนาบน branch แยกตามงาน: `feat/v7-a-onestop`, `feat/v7-b-online`, `feat/v7-c-fast`,
   `feat/v7-d-pwa`, `feat/v7-e-rates`
3. ก่อนเปิด PR: `uv run pytest` ผ่านทุกตัว · `manage.py check` ไม่มี issue ·
   `makemigrations --check --dry-run` ไม่มี migration ตกค้าง
4. PR ที่มี migration: pipeline B0 (build → migrate → deploy) มีแล้ว — ระบุใน PR ว่ามี migration
   และหลัง merge ตรวจ Cloud Build → History ว่าผ่านครบ 3 ขั้น
5. เจ้าของระบบสั่ง **"merge PR #..."** ชัดเจนเท่านั้นจึง merge ได้
6. กฎธุรกิจอยู่ใน `services.py` เท่านั้น · ข้อความผู้ใช้เป็นไทย/พ.ศ. · schema แบบ expand/contract
7. ห้ามเริ่มงานถัดไปก่อนงานปัจจุบันถูก merge — ติดคำถามเชิงออกแบบให้ถามใน PR

## งาน A — หน้าแรกแบบ One-Stop: "วันนี้จะใช้ห้องแบบไหน" (ไม่มี migration)

**ปัญหา:** ทางเข้าแต่ละประเภทกระจายอยู่ในเมนู ผู้ใช้ใหม่ไม่รู้จะเริ่มตรงไหน
และต้องกรอกฟอร์มค้นหาก่อนจึงเห็นห้องว่าง

**ให้ทำ:**
1. ปรับหน้าแรก (หลัง login และหน้า guest) เพิ่มส่วนบนสุดเป็น **การ์ดทางเข้า — งาน A ทำ 3 ใบ**
   ปุ่มใหญ่กดง่ายบนมือถือ (ออกแบบ layout ให้รับใบที่ 4 ได้โดยไม่ต้องแก้โครง แต่**งาน A ห้ามอ้าง
   `Resource.Category.ONLINE`** เพราะหมวดนี้ยังไม่เกิดจนถึงงาน B — งาน B เป็นผู้เพิ่มการ์ดออนไลน์ให้ครบ 4 ใบ):
   - ห้องเรียน/ห้องสอนปฏิบัติ (`classroom` + `lab`)
   - ห้องประชุม (`meeting` + `special`)
   - **ห้องพักหลักสูตร — เส้นทางต่างจากสองใบแรก:** ห้องพักจองตาม **วันเข้า–ออกของหลักสูตร**
     ไม่ใช่รายชั่วโมง การ์ดใบนี้จึงแสดง **รายการหลักสูตรที่เปิดรับ (`is_active`) ตรง ๆ บนหน้าแรก**
     กดชื่อหลักสูตรแล้วเข้าเว็บเลือกเตียง (portal เดิม) ทันที — เส้นทางคือ
     กดหลักสูตร → เลือกเตียง → ยืนยัน = 3 คลิก **ห้ามลิงก์ผ่านหน้า lodging index คั่นกลาง**
     (ถ้าไม่มีหลักสูตรเปิดรับ แสดงข้อความ "ยังไม่มีหลักสูตรเปิดรับเข้าพัก" แทน)
2. ใต้การ์ด: แถบ **"ว่างตอนนี้ — จองเลย"** ต่อกลุ่ม — **งาน A มี 2 กลุ่มรายชั่วโมง**
   (ห้องเรียน/ปฏิบัติ และห้องประชุม — ไม่รวมห้องพักซึ่งจองรายหลักสูตร; งาน B เพิ่มออนไลน์เป็นกลุ่มที่ 3)
   แสดงห้องที่ว่างในช่วงถัดไป (สูงสุด 4 ห้อง/หมวด พร้อมรูปหน้าปกจาก V6-C)
   ปุ่ม "จองเลย" พาเข้าฟอร์มจองแบบ prefill วัน-เวลาให้เสร็จ = การ์ดหมวด → จองเลย → ยืนยัน = 3 คลิก
3. **สูตรเวลา "ว่างตอนนี้" (ต้องตามนี้ ห้ามใช้เวลาปัจจุบันตรง ๆ):**
   - เวลาเริ่ม = ปัดเวลาปัจจุบัน**ขึ้น**เป็นช่วง 15 นาทีถัดไป (10:07 → 10:15) · ระยะเวลา default 60 นาที
     — สอดคล้องกฎเดิมใน `bookings/services.py` (ช่วงละ 15 นาที, ห้ามเริ่มในอดีต)
   - ห้องที่แสดงต้องผ่าน **เส้นทางตรวจเดิมทั้งชุด**: ตรวจชน, blackout, outage, เวลาเปิดบริการ,
     buffer และสิทธิ์หน่วย (`allowed_units`) ของผู้ใช้คนนั้น — ห้องที่ผู้ใช้ไม่มีสิทธิ์ **ไม่แสดง**
     ห้ามเขียนเงื่อนไขตรวจซ้ำใหม่ ให้เรียก service เดิม
   - **กรอกฟอร์มช้าจนเวลาเริ่มผ่านไป:** validate เดิมจะฟ้อง "เวลาเริ่มต้องไม่อยู่ในอดีต" —
     ให้เพิ่มปุ่ม "เลื่อนเป็นช่วงถัดไป" ข้าง error นั้น กดครั้งเดียวปัดเวลาใหม่ให้แล้วส่งซ้ำได้
   - **มีคนจองแทรกก่อนยืนยัน:** ExclusionConstraint + ตรวจชนเดิมจะฟ้องชนตามปกติ —
     ไม่ต้องทำกลไกใหม่ แต่ต้องมีเทส cover เส้นทางนี้จากปุ่มจองเลย และข้อความ error
     ต้องแนะนำให้กลับไปเลือกห้อง/ช่วงอื่น
4. **ให้เป้า "เหลือกรอกชื่อกิจกรรมแล้วยืนยัน" เป็นจริง:** ฟอร์มจองต้อง prefill
   `responsible_name`/`responsible_phone` จากโปรไฟล์ผู้ใช้ (`User.phone`) —
   ถ้าโปรไฟล์ไม่มีเบอร์ ให้ผู้ใช้กรอกในฟอร์มแล้ว **บันทึกกลับเข้าโปรไฟล์อัตโนมัติ**
   (logic ใน `services.py` — เขียนทับเฉพาะเมื่อโปรไฟล์ว่าง) เพื่อให้ครั้งถัดไปไม่ต้องกรอกอีก
5. ตรรกะ "ว่างตอนนี้" เขียนใน `bookings/services.py` (ฟังก์ชันใหม่ ห้ามเขียนใน view) ·
   การ์ดหมวดใช้จำนวนห้องจริงจาก `Resource.Category` ไม่ hardcode ·
   CSS เพิ่มใน `static/css/app.css` ตามธีมเดิม ห้าม inline style

**เทส:** service "ว่างตอนนี้" (ปัดเวลา 10:07→10:15 · ตัดห้องชน/งดใช้/blackout/ไม่มีสิทธิ์หน่วย · จำกัดจำนวน) ·
หน้าแรกมีหลักสูตรเปิดรับและลิงก์ตรงเข้า portal · ปุ่มจองเลยแนบ prefill ถูกต้อง ·
จองแทรกแล้ว error พร้อมคำแนะนำ · เบอร์โทรบันทึกกลับโปรไฟล์เฉพาะเมื่อเดิมว่าง

**ดูผล:** มือถือ → หน้าแรกเห็นการ์ด 3 ใบ (ห้องเรียน · ประชุม · ห้องพัก) + หลักสูตรเปิดรับ + ห้องว่างตอนนี้ → กด "จองเลย" →
ฟอร์มเติมวัน-เวลา-ชื่อ-เบอร์ให้แล้ว เหลือชื่อกิจกรรม → ยืนยัน → เห็นชัดว่า "อนุมัติแล้ว" หรือ "รออนุมัติ"

## งาน B — หมวดใหม่ "ห้องสอนออนไลน์" (มี migration — expand)

**ให้ทำ:**
1. เพิ่ม `Resource.Category.ONLINE = "online", "ห้องสอนออนไลน์"` (choices เปลี่ยน → migration เล็ก 1 ไฟล์)
   และ**เพิ่มการ์ดใบที่ 4 "ห้องสอนออนไลน์" บนหน้าแรกของงาน A** (แสดงเมื่อมีห้องหมวดนี้อย่างน้อย 1 ห้อง
   มิฉะนั้นซ่อน) — หน้าแรกจึงครบ 4 ใบเมื่อปิดงานนี้
2. เพิ่มฟิลด์ `Booking.online_meeting_url` (URLField, blank) — ลิงก์ห้องเรียนออนไลน์ของครั้งนั้น:
   - ช่องนี้แสดงในฟอร์มจอง **เฉพาะห้องหมวด online** (เงื่อนไขในฟอร์ม/เทมเพลต)
   - **สิทธิ์ดูลิงก์ — เข้มกว่า `can_view_details()` เดิม:** เพิ่มฟังก์ชันใหม่
     `can_view_online_link(user, booking)` ใน `bookings/services.py` อนุญาตเฉพาะ
     (ก) ผู้จอง (ข) superuser / infosec officer (ค) เจ้าหน้าที่ดูแลห้องและผู้อนุมัติของห้องนั้น —
     **คนหน่วยเดียวกันดูรายละเอียดอื่นได้ตาม `can_view_details()` เดิม แต่ไม่เห็นลิงก์**
     ทุกจุดที่แสดงลิงก์ต้องเรียกฟังก์ชันนี้เท่านั้น
   - **ข้อความแจ้งเตือนห้ามฝังลิงก์ประชุม** — ให้พาไปหน้ารายละเอียดการจอง
     (ซึ่งตรวจ `can_view_online_link` อีกครั้ง) เหตุผล: ข้อความแจ้งเตือนเป็นข้อมูลถาวร
     แก้สิทธิ์/แก้ลิงก์ย้อนหลังไม่ได้
3. `seed_pilot` เพิ่มห้องตัวอย่าง 3 ห้อง — **ตามข้อมูลจริงจากเจ้าของระบบ: ห้องสอนออนไลน์มี
   ประมาณ 3 ห้อง อยู่ที่ บก.กศ.รร.ส.สส.** สเปคเหมือนกันทุกช่อง ต่างเฉพาะรหัส/ชื่อ:
   `STU-ONLINE-1/2/3` "ห้องสอนออนไลน์ 1/2/3" (อาคาร บก.กศ. · นโยบาย AUTO ·
   buffer ก่อน 0 / หลังใช้ 15 นาที · ความจุ 5 · หน่วยเจ้าของ EDU ·
   อุปกรณ์ประจำห้อง: กล้อง/ไมค์/ไฟสตูดิโอ/จอเขียว) — seed สำหรับ dev/test เท่านั้น
4. **การขึ้น production (pipeline ไม่รัน seed ใด ๆ — ห้ามรัน `seed_pilot` บน production
   เพราะแตะข้อมูลตั้งต้นชุดอื่นด้วย):** ขั้นส่งมอบของงานนี้คือ หลัง merge + Cloud Build ผ่านครบ
   ให้ Claude พาเจ้าของระบบ**สร้างห้องออนไลน์ 3 ห้องผ่าน Django Admin บนเว็บจริง** (ใช้รหัส/ชื่อห้องจริงของ บก.กศ.)
   ตามสเปคข้อ 3 ทีละช่อง แล้วยืนยันว่าการ์ด "ห้องสอนออนไลน์" โผล่บนหน้าแรก production
   จึงถือว่าปิดงาน B (แบบเดียวกับประตูที่ 2 ของ V6-C)
5. รายงานสรุปการใช้ (S16) ต้องรวมหมวดใหม่ — ถ้ามี hardcode หมวดที่ใด แก้เป็นวนตาม choices
6. ห้ามแตะกฎกันจองซ้อน — หมวดใหม่ใช้ ExclusionConstraint เดิมโดยอัตโนมัติ

**เทส (ครอบ 4 มุมมองสิทธิ์):** ผู้จองเห็นลิงก์ · **คนหน่วยเดียวกันเห็นรายละเอียดแต่ไม่เห็นลิงก์** ·
คนต่างหน่วยเห็น masked · guest ไม่เห็นอะไร · แจ้งเตือนไม่มี URL ประชุมในเนื้อความ ·
ฟอร์มห้องหมวดอื่นไม่มีช่องลิงก์ · การ์ดออนไลน์บนหน้าแรกแสดงเมื่อมีห้อง/ซ่อนเมื่อไม่มี ·
migration ไม่กระทบข้อมูลเดิม

**ให้ทำ:**
1. **ปุ่ม "จองแบบเดิมอีกครั้ง"** ในหน้า "การจองของฉัน" ทุกใบที่อนุมัติแล้ว/ใช้แล้ว →
   เปิดฟอร์มจองห้องเดิม prefill ทุกช่องจากครั้งก่อน โดย **วันที่ default ต้องห่างจากวันเดิม
   อย่างน้อย 7 วันเสมอ** — สูตรตายตัว (กันได้ทั้งวันในอดีตและกันชนกับการจองต้นฉบับที่ยังมาไม่ถึง):

   (จองสัปดาห์ล่าสุด → +7 วันพอดี · จองเก่าเมื่อเดือนก่อน → วันเดียวกันของสัปดาห์หน้า ·
   **จองต้นฉบับเป็นวันพรุ่งนี้ → ได้พรุ่งนี้ของสัปดาห์ถัดไป ไม่ใช่วันพรุ่งนี้ซ้ำ**)

2. **ช่วงเวลาสำเร็จรูป** — ปุ่ม "คาบเช้า 0800–1200" · "คาบบ่าย 1300–1600" · "ทั้งวัน 0800–1600":
   - **ตำแหน่งที่วาง (ฟอร์มจองมี 2 โหมด — ดู `templates/bookings/partials/booking_fields.html`):**
     วางเฉพาะจุดที่**ช่องเวลาแสดงจริง**เท่านั้น คือ (ก) หน้า "ค้นหาห้องว่าง" เหนือช่องเวลา และ
     (ข) ฟอร์มจองโหมดที่แสดงส่วน "วันและเวลา" —
     **ห้ามวางในโหมดสรุปการจอง** (โหมดที่ date/start/end เป็น hidden field) เพราะปุ่มจะแก้ค่า hidden
     โดยข้อความสรุปไม่เปลี่ยนตาม ผู้ใช้จะเห็นเวลาหนึ่งแต่ระบบส่งอีกเวลา — โหมดนั้นให้ใช้ลิงก์
     "เปลี่ยนวัน/เวลา ←" เดิมพากลับไปแก้ที่หน้าค้นหา
   - กดแล้วต้องอัปเดต input `start_time`/`end_time` จริงที่ browser ส่ง (JS เล็กในเทมเพลตได้
     เพราะเป็นตัวช่วยกรอก ไม่ใช่กฎธุรกิจ)
   - ช่วงเวลาแก้ได้ใน Admin ผ่าน `ReferenceValue` (field ใหม่ `time_preset` ค่าเช่น `0800-1200|คาบเช้า`)
     — **ต้องมี validation ตอนบันทึกใน Admin:** รูปแบบ `HHMM-HHMM|ป้ายชื่อ` เท่านั้น, เวลาเริ่ม < เวลาสิ้นสุด,
     ตรงช่วง 15 นาที — ห้ามรับสตริงทุกค่าแล้วไปพังตอนแสดงผล
3. **ห้องโปรด:** M2M `User.favorite_resources` (migration expand 1 ไฟล์) — ปุ่มดาวบนการ์ดห้อง
   ห้องโปรดขึ้นก่อนในผลค้นหาและแถบ "ว่างตอนนี้" ของงาน A

**เทส:** rebook prefill ครบ — จองสัปดาห์ล่าสุดได้ +7 วันเวลาเดิม · **จองเก่าเมื่อเดือนก่อนได้วันเดียวกัน
ของสัปดาห์หน้า (ไม่ใช่วันในอดีต)** · ตรวจชนยังทำงาน · time_preset เรียงลำดับ/ปิดใช้ได้ ·

## งาน E — เรตราคาห้องพัก: ห้องปรับอากาศ/ห้องพัดลม + มิเตอร์แอร์ (มี migration — expand)

**ความต้องการจากเจ้าของระบบ:** ห้องพักมี 2 ประเภทคือ **ห้องปรับอากาศ** และ **ห้องพัดลม** —
ห้องปรับอากาศคิดค่าที่พัก **วันละ 100 บาท** และค่าไฟจาก **มิเตอร์แอร์หน่วยละ 5 บาท**

**คำถามที่เจ้าของระบบต้องตอบก่อนเริ่มงาน E (5 ข้อ — ห้ามผู้พัฒนาสันนิษฐานเอง):**
1. ห้องพัดลมคิดค่าที่พักวันละเท่าไหร่ หรือไม่คิดเลย?
2. ค่าไฟมิเตอร์แอร์เป็นของ **ทั้งห้อง** (4 เตียง) — แบ่งจ่ายอย่างไร: หารเท่ากันตามจำนวนผู้เข้าพักจริง
   หรือคิดเหมารายห้องให้หัวหน้าห้องรับผิดชอบ?
3. ระบบต้องแค่ **คำนวณและแสดงยอด** (ผู้ใช้ไปจ่ายเงินสด/ช่องทางเดิมเอง) หรือต้อง **บันทึกสถานะรับชำระ** ด้วย?
   (แนะนำเริ่มจากคำนวณ+แสดงยอด+export ก่อน — เรื่องรับเงินมีภาระตรวจสอบทางการเงินตามมา)
4. **100 บาท/วัน คิดต่อคนหรือต่อห้อง?** (ห้อง 4 เตียง ถ้าคิดต่อห้องแล้วพัก 3 คน ยอดต่อคนต่างกันมาก)
5. **นับวันอย่างไร:** รวมทั้งวันเข้าและวันออก = `(check_out - check_in).days + 1` หรือคิดเป็นจำนวนคืน
   = `(check_out - check_in).days`? — หมายเหตุ: ระบบปัจจุบันสงวนห้อง**รวมวันออกด้วย**
   (`bookings/lodging_services.py`) ถ้าตั้งใจคิดทุกวันที่ครอบครองห้อง สูตรคือแบบ `+1`

**ให้ทำ (หลังได้คำตอบครบ):**
1. `Resource` เพิ่มฟิลด์ `lodging_room_kind` (choices: `air` "ห้องปรับอากาศ" / `fan` "ห้องพัดลม")
   — migration expand · **blank ได้เฉพาะช่วงเปลี่ยนผ่านหลัง migration เท่านั้น**: ระบบต้อง**ปฏิเสธ
   การออกใบสรุปค่าใช้จ่าย**ของรอบใดก็ตามที่ยังมีห้องในรอบไม่ได้ตั้งประเภท (แจ้งรายชื่อห้องที่ขาด)
   · ตั้งค่าใน Admin · หน้าเลือกเตียงแสดงป้ายประเภทห้องและเรตราคาบนการ์ดให้เห็น**ก่อน**เลือกเตียง
2. โมเดลอัตราค่าบริการแก้ได้ใน Admin (**ห้าม hardcode ราคาในโค้ด**): ค่าที่พัก/วัน แยกตามประเภทห้อง
   และค่าไฟ/หน่วย — ค่าเริ่มต้น: ปรับอากาศ 100 บาท/วัน · ไฟมิเตอร์แอร์ 5 บาท/หน่วย ·
   ห้องพัดลมตามคำตอบข้อ 1
3. **Snapshot เรตต่อรอบ — กันยอดย้อนหลังเปลี่ยนเมื่อ Admin แก้เรต:** เมื่อบันทึกเลขมิเตอร์ปิดรอบ
   (หรือกดปิดการคิดเงินของรอบ) ให้**คัดลอกเรตที่ใช้จริง ณ ขณะนั้นเก็บลงเรคคอร์ดของรอบ**
   การคำนวณ/ใบสรุป/CSV ของรอบที่ปิดแล้วต้องอ่านจาก snapshot เท่านั้น — แก้เรตใน Admin
   ภายหลัง (เช่น 100 → 120) ต้องกระทบเฉพาะรอบใหม่ พร้อมเทสยืนยัน
4. บันทึก **เลขมิเตอร์แอร์ต่อห้องต่อรอบหลักสูตร** ในหน้าจัดการที่พักหลักสูตร — สเปคโมเดล:
   `DecimalField` ห้ามติดลบ · เลขออก ≥ เลขเข้า · **unique constraint `(cohort, room)`** ·
   validate ว่าห้องนั้นอยู่ในรอบหลักสูตรนั้นจริง
5. ระบบคำนวณยอดต่อห้อง/ต่อคน: ค่าที่พัก = จำนวนวันตามสูตรที่ตอบในข้อ 5 ของคำถาม × เรตประเภทห้อง
   (ต่อคนหรือต่อห้องตามคำตอบข้อ 4) · ค่าไฟ = (เลขออก − เลขเข้า) × เรตต่อหน่วย —
   **นิยาม "ผู้เข้าพักจริง" = ผู้ที่เช็กอินแล้ว (`checked_in_at` ไม่ว่าง) ณ เวลาปิดรอบ** ·
   **การปัดเศษเมื่อหารไม่ลงตัว:** คิดเป็นสตางค์ (Decimal 2 ตำแหน่ง) แล้วให้ผลรวมรายคน
   เท่ายอดจริงของห้องเสมอ — เศษที่เหลือจากการหารให้ผู้พักเตียงหมายเลขน้อยสุดรับ ·
   สูตรทั้งหมดอยู่ใน `services.py` พร้อมเทสตัวเลขตรง ๆ
6. **ใบสรุปค่าใช้จ่าย**: หน้าเว็บต่อหลักสูตร (ยอดรายห้อง/รายคน — เฉพาะผู้กำกับหลักสูตร/เจ้าหน้าที่) +
   export CSV แบบเดียวกับทะเบียนผู้เข้าพักเดิม
7. **Student pass เปิดได้โดยไม่ login (UUID)** — บนบัตรแสดงได้เฉพาะ **ยอดของเจ้าของบัตรคนเดียว**:
   ห้ามแสดงยอดรวมห้อง เลขมิเตอร์ หรือยอดของเพื่อนร่วมห้อง เด็ดขาด
8. หลักสูตรเก่าที่ไม่มีเลขมิเตอร์ = ไม่แสดงยอดค่าไฟ (ไม่ error) — ข้อมูลเดิมไม่กระทบ
9. **ขั้นปิดงาน E (เพราะ E แก้หน้าที่งาน D ตรวจไปแล้ว):** รัน `uv run pytest` ทั้งชุด และ
   **ตรวจ 360px ซ้ำอย่างน้อย 3 หน้า**: portal เลือกเตียง · student pass · หน้าใบสรุป/รายงาน
   พร้อมภาพหน้าจอแนบ PR — ผ่านครบจึงปิด V7

**เทส:** สูตรคำนวณ (วันพัก × เรต ตามแบบต่อคน/ต่อห้อง, หน่วยไฟ × เรต, การแบ่งจ่าย+ปัดเศษรวมแล้ว
เท่ายอดจริง) · snapshot เรต — แก้เรตใน Admin แล้วรอบที่ปิดแล้วยอดไม่เปลี่ยน · validation มิเตอร์
(ติดลบ/ออก<เข้า/ห้องนอกรอบ/ซ้ำ (cohort, room)) · ใบสรุปถูกปฏิเสธเมื่อมีห้องยังไม่ตั้งประเภท ·
ห้องพัดลมไม่มีค่าไฟแอร์ · หลักสูตรเก่าไม่มีมิเตอร์ไม่ error · **student pass ไม่มียอดรวมห้อง/
เลขมิเตอร์/ข้อมูลเพื่อนร่วมห้อง** · เรตอ่านจาก Admin ไม่ hardcode

**ดูผล:** ตั้งประเภทห้อง DORM-101 = ปรับอากาศ → กรอกมิเตอร์เข้า 1000 ออก 1050 →
ใบสรุปแสดง ค่าที่พัก (จำนวนวัน × เรต) + ค่าไฟ 50 หน่วย × 5 = 250 บาท ตรงตามคำนวณมือ →
แก้เรตใน Admin เป็น 120 → ใบสรุปรอบเดิมยอดไม่เปลี่ยน

## ลำดับการทำและการส่งมอบ

1. งาน A → PR → Claude ตรวจ → เจ้าของสั่ง merge → ดูผลบนเว็บจริง
2. งาน B → PR (มี migration — ตรวจ Cloud Build ครบ 3 ขั้นหลัง merge) → **สร้างห้องออนไลน์ผ่าน Admin
   บน production ตามงาน B ข้อ 4** → เห็นการ์ดออนไลน์บนเว็บจริงจึงปิดงาน
3. งาน C → PR (มี migration) → ดูผลบนเว็บจริง
4. งาน D → PR → ดูผล → **วัดตัวชี้วัดทั้ง 5 ข้อ บันทึกผลราย คน/หน้า/เครื่อง ใน `docs/v7-notes.md`**
5. งาน E → เจ้าของระบบตอบคำถามครบ 5 ข้อของงาน E ก่อน → PR (มี migration) → ตั้งประเภทห้อง+เรตจริง
   ผ่าน Admin บน production → ดูใบสรุปตรงกับคำนวณมือ → **regression pytest ทั้งชุด + ตรวจ 360px ซ้ำ
   3 หน้าตามงาน E ข้อ 9** → ปิด V7
