1. ภาพรวมและขอบเขต

1.1 เป้าหมาย

  • ตรวจสอบห้องว่างได้ทันที และป้องกันการจองเวลาซ้ำ
  • รองรับการอนุมัติตามสายงาน พร้อมผู้อนุมัติสำรองและเส้นตาย
  • แสดงตารางใช้ห้องรายวัน รายสัปดาห์ รายเดือน
  • เก็บประวัติทุกการกระทำ: ใครจอง ใครอนุมัติ ใครแก้ไข ใครสั่งย้าย
  • ให้เจ้าหน้าที่บริหารห้องและอุปกรณ์จากจุดเดียว
  • ใช้งานง่ายบนคอมพิวเตอร์และมือถือ รองรับผู้ใช้ที่มีทักษะดิจิทัลต่างกัน
  • วางสถาปัตยกรรมให้กฎการจอง การอนุมัติ และการตรวจเวลาชนทำงานถูกต้องภายใต้ภาระใช้งานจริง
  • พัฒนา ทดสอบ และดูแลระบบตามมาตรฐานความปลอดภัยและคุณภาพซอฟต์แวร์ที่ตรวจรับได้

1.2 อยู่ในขอบเขตระยะที่ 1

ทะเบียนห้องและอุปกรณ์ส่วนกลาง · ปฏิทิน · จองครั้งเดียวและจองเป็นชุด · ตรวจเวลาชนรวม buffer · อนุมัติ/ปฏิเสธ/สำรอง/หมดอายุ · บังคับย้าย · บันทึก no-show โดยเจ้าหน้าที่ · แจ้งเตือนในระบบและ LINE · audit log · รายงานพื้นฐาน · 2FA

1.3 นอกขอบเขตระยะที่ 1

เช็กอิน QR Code · รายการเตรียมห้อง (checklist) · เชื่อม AD/LDAP · เชื่อมตารางเรียนและปฏิทินองค์กร · จอหน้าห้อง — กำหนดไว้ในระยะที่ 2–3

เลือกวัน-เวลา และจำนวนผู้เข้าร่วม ↓ ระบบแสดงทรัพยากรที่ว่าง (คำนวณรวม buffer และปฏิทินส่วนกลาง) ↓ กรอกรายละเอียดกิจกรรม อุปกรณ์ส่วนกลาง การจัดโต๊ะ การมองเห็น ↓ ตรวจเวลาชนอีกครั้งขณะบันทึก (ล็อกระดับฐานข้อมูล) ↓ นโยบาย "อัตโนมัติ" → อนุมัติ → แจ้งผู้จอง + จนท.ดูแลห้อง นโยบาย "ต้องอนุมัติ" → รออนุมัติ → ส่งผู้อนุมัติหลัก (ข้อ 7) ↓ บันทึก audit log ทุกขั้น

6.1 ข้อกำหนดฟังก์ชัน

FR-01ผู้ใช้ค้นหาทรัพยากรว่างได้จาก วัน-เวลา ประเภทห้อง อาคาร ความจุ และอุปกรณ์ประจำห้อง FR-02ปฏิทินแสดงมุมมองรายวัน รายสัปดาห์ รายเดือน ต่อห้องและต่อกลุ่มห้อง FR-03การจองหนึ่งรายการเก็บข้อมูลตามข้อ 12.2 ครบทุกฟิลด์บังคับจึงส่งได้ FR-04ผู้จองแก้ไขหรือยกเลิกได้เองจนถึงเส้นตายของห้อง หลังเส้นตายต้องให้เจ้าหน้าที่ดูแลห้องหรือผู้ดูแลระบบดำเนินการ และบันทึกเหตุผล FR-05การแก้ไขหลังอนุมัติแบ่งฟิลด์เป็นสามกลุ่ม: (ก) ฟิลด์ที่กระทบการจัดสรร — วัน-เวลา ห้อง รายการอุปกรณ์ส่วนกลาง · (ข) ฟิลด์ที่กระทบนโยบายอนุมัติ — หน่วยงานผู้ขอ ผู้เข้าร่วมจากภายนอก จำนวนผู้เข้าร่วมที่ทำให้เกินความจุ (วัน-เวลาและห้องอยู่ทั้งสองกลุ่ม) · (ค) ฟิลด์ทั่วไป — ที่เหลือทั้งหมด การแก้กลุ่ม (ก) หรือ (ข) ของการจองที่อนุมัติแล้ว ไม่แก้การจองเดิมโดยตรง แต่สร้าง คำขอแก้ไข (amendment) ตามข้อ 6.4 กลุ่ม (ค) แก้ได้ทันทีโดยไม่อนุมัติใหม่ · "ระดับการมองเห็น" ไม่อยู่ใน workflow อนุมัติห้อง: ปกติ→จำกัด ทำได้ทันที จำกัด→ปกติ ต้องยืนยันซ้ำ (SR-07) · ทุกการแก้บันทึกใน audit log FR-06ระยะที่ 1 คำขอหนึ่งมี ห้องได้หนึ่งห้อง และอุปกรณ์ส่วนกลางได้หลายรายการ ระบบตรวจชนทั้งห้องและอุปกรณ์พร้อมกัน ถ้าชนอย่างใดอย่างหนึ่งต้องแจ้งให้ชัดว่าชนที่ไหน การใช้หลายห้องในกิจกรรมเดียวให้ส่งหลายคำขอ (ระบบช่วยคัดลอกรายละเอียดให้) การจองหลายห้องในคำขอเดียวพร้อมอนุมัติจากเจ้าของทุกห้องกำหนดไว้ระยะที่ 2

6.2 การตรวจเวลาชน

FR-07ช่วงเวลาที่ถือครองทรัพยากร = [start − buffer_before, end + buffer_after) สองการจองชนกันเมื่อช่วงถือครองซ้อนทับ FR-08ปฏิทินและการแจ้งเตือนแสดง start–end ของกิจกรรมจริงเท่านั้น buffer แสดงเป็นแถบจางและไม่แสดงชื่อกิจกรรม FR-09การตรวจชนต้องทำซ้ำขณะบันทึกภายใต้ล็อก เพื่อป้องกันสองคำขอพร้อมกันผ่านการตรวจทั้งคู่ บังคับที่ฐานข้อมูลด้วย exclusion constraint บน BOOKING_RESOURCE(resource, hold_range) เฉพาะแถวที่ released_at IS NULL FR-10นโยบายมาก่อนได้ก่อน: สถานะที่ถือครองเวลา: รออนุมัติ, อนุมัติ · ไม่ถือครอง: ร่าง, ปฏิเสธ, ยกเลิก, หมดอายุ คำขอที่ส่งก่อนจึงกันห้องไว้แม้ยังไม่อนุมัติ และผู้อื่นเห็นช่วงนั้นเป็น "รออนุมัติ" เมื่อคำขอถูกปฏิเสธ ยกเลิก หมดอายุ หรือถูกย้าย ระบบตั้ง released_at ให้แถวถือครองทันที ช่วงเวลาจึงว่างให้ผู้อื่น การต่อคิว (waitlist) กำหนดไว้ระยะที่ 2 FR-11ปฏิทินส่วนกลาง (วันหยุดราชการ พิธี กิจกรรมรวม) แต่ละรายการมีขอบเขตเป็น ทุกห้อง / อาคาร / ประเภทห้อง / ห้องที่เลือก และบล็อกเฉพาะขอบเขตนั้น FR-12ห้องสถานะ "งดใช้ชั่วคราว" บล็อกการจองใหม่ในช่วงนั้น และระบบแสดงรายการจองที่ได้รับผลกระทบให้เจ้าหน้าที่จัดการ (ย้ายหรือยกเลิก) พร้อมแจ้งผู้จองทุกราย

6.3 การจองเป็นชุด

FR-13ชุดการจอง (booking_series) กับการจองรายครั้ง (booking) เป็นคนละเอนทิตี แต่ละครั้งแก้ไข/ยกเลิกได้อิสระโดยไม่กระทบครั้งอื่น FR-14รองรับรูปแบบ รายวัน รายสัปดาห์ (เลือกหลายวันในสัปดาห์) และรายการวันที่กำหนดเอง พร้อมวันสิ้นสุดหรือจำนวนครั้ง FR-15ก่อนยืนยัน ระบบแสดงรายการทุกครั้งพร้อมระบุครั้งที่ชน (และชนกับอะไรตามสิทธิ์มองเห็น) ให้ผู้ใช้เลือก: จองเฉพาะครั้งที่ว่าง / กลับไปเปลี่ยนเวลา / ยกเลิกทั้งชุด FR-16ชุดที่ต้องอนุมัติส่งเป็นคำขอเดียว ผู้อนุมัติอนุมัติ/ปฏิเสธทั้งชุดในครั้งเดียว แต่สามารถตัดบางครั้งออกได้พร้อมเหตุผล FR-17ครั้งที่ตรงกับปฏิทินส่วนกลางที่บล็อกห้องนั้นจะถูกข้ามอัตโนมัติ และแสดงในรายการว่า "ข้าม: <เหตุผล>"

6.4 การแก้ไขหลังอนุมัติ (Amendment)

หลักการ: ผู้ที่ได้รับอนุมัติแล้วต้องไม่เสียห้องเพราะยื่นขอแก้ไข การจองเดิมจึงคงช่วงถือครองไว้จนกว่าการแก้ไขจะได้รับอนุมัติ

ผู้จองยื่น amendment (ค่าใหม่ของฟิลด์กลุ่ม ก/ข) ↓ ระบบตรวจชนช่วงใหม่ → ถือครองช่วงใหม่ "ชั่วคราว" (แถว BOOKING_RESOURCE ที่มี amendment_id) การจองเดิมยังถือครองช่วงเดิมตามปกติ ↓ ประเมินนโยบายจากค่าใหม่ (ห้องใหม่ + ฟิลด์กลุ่ม ข) "อัตโนมัติ" → อนุมัติ amendment ทันที "ต้องอนุมัติ" → ส่งผู้อนุมัติของห้องปลายทาง (SLA/เร่งด่วน/หมดอายุ ตาม FR-21–23) ↓ อนุมัติ → transaction เดียว: ปลดช่วงเดิม + เปิดใช้ช่วงใหม่ + เขียนค่าใหม่ลงการจอง ปฏิเสธ / หมดอายุ / ผู้จองถอน → ปลดช่วงใหม่ การจองเดิมไม่เปลี่ยน
FR-34amendment เป็นเอนทิตีแยก (BOOKING_AMENDMENT) เก็บค่าที่เสนอของฟิลด์กลุ่ม (ก)/(ข) สถานะ รออนุมัติ / อนุมัติ / ปฏิเสธ / หมดอายุ / ถอน ผู้ยื่น เวลายื่น และผลการตัดสิน การจองเดิมไม่ถูกแก้จนกว่า amendment จะอนุมัติ FR-35ช่วงถือครองที่เสนอเป็นแถว BOOKING_RESOURCE ที่มี amendment_id และอยู่ภายใต้ exclusion constraint เดียวกับ FR-09 หากช่วงใหม่ชน ระบบปฏิเสธการยื่นทันทีและการจองเดิมไม่เปลี่ยน · ช่วงใหม่ที่ซ้อนกับช่วงเดิมของการจองเดียวกัน (เช่น ขยายเวลา) ไม่ถือว่าชนกันเอง FR-36การจองหนึ่งมี amendment สถานะ "รออนุมัติ" ได้ ครั้งละหนึ่งรายการ (unique partial index) ผู้จองต้องถอนรายการเดิมก่อนยื่นใหม่ · amendment หมดอายุตามเกณฑ์ FR-22 โดยนับจากเวลาเริ่มที่ เร็วกว่า ระหว่างช่วงเดิมกับช่วงใหม่ และใช้ SLA/เร่งด่วนตาม FR-21/FR-23 · ข้อจำกัดสองข้อนี้ป้องกันการกันหลายช่วงเวลาไว้พร้อมกัน FR-37ผู้อนุมัติของ amendment คือผู้อนุมัติของ ห้องปลายทาง (ห้องเดิมถ้าไม่เปลี่ยนห้อง) หากเปลี่ยนห้องข้ามเจ้าของ ผู้อนุมัติของห้องเดิมได้รับแจ้งเพื่อทราบ ไม่ต้องอนุมัติ · ผู้อนุมัติเห็นค่าเดิมและค่าใหม่เทียบกัน · APPROVAL ของ amendment บันทึก amendment_id และผลการตัดสินเช่นเดียวกับคำขอปกติ FR-38เมื่ออนุมัติ ระบบทำใน transaction เดียว: ตั้ง released_at ให้แถวถือครองเดิม → ล้าง amendment_id ของแถวถือครองใหม่ให้กลายเป็นแถวถือครองหลัก → เขียนค่าใหม่ลง BOOKING → ปิด amendment เป็น "อนุมัติ" ล้มเหลวขั้นใดให้ย้อนกลับทั้งหมด · เมื่อปฏิเสธ/หมดอายุ/ถอน ตั้ง released_at ให้แถวถือครองใหม่เท่านั้น · แจ้งผู้จอง ผู้อนุมัติ และเจ้าหน้าที่ดูแลห้องทั้งห้องเดิมและห้องใหม่ทุกกรณี · การแก้ไขการจองในห้องนโยบายอัตโนมัติที่ผลประเมินยังเป็น "อัตโนมัติ" ใช้กลไกเดียวกันแต่อนุมัติทันทีภายใน transaction เดียวกับการยื่น

7. การอนุมัติ

FR-18คำขอถูกส่งให้ primary_approver ของ ห้อง ในคำขอ (คำขอละหนึ่งห้องตาม FR-06 จึงมีผู้อนุมัติคนเดียว) หากอยู่ในช่วงที่ผู้อนุมัติหลักตั้งผู้รักษาการ ส่งตรงผู้รักษาการตาม FR-20 อุปกรณ์ส่วนกลางในคำขอไม่ต้องอนุมัติแยก · กฎเดียวกันใช้กับ amendment โดยยึดห้องปลายทาง (FR-37) FR-19ยกเลิกใน 0.2 — การจัดสรรอัตโนมัติระหว่างคำขอที่ชนกันขัดกับนโยบายมาก่อนได้ก่อน (FR-10) เพราะคำขอที่สองจะบันทึกไม่ได้ตั้งแต่ต้น คงเลขไว้เพื่อไม่ให้การอ้างอิงเลื่อน FR-20ผู้อนุมัติหลักตั้งผู้รักษาการแทนได้เอง ระบุช่วงวันที่เริ่ม-สิ้นสุด ทุกการอนุมัติบันทึก acted_by และ on_behalf_of FR-21SLA: คำขอค้างเกิน 2 วันทำการ (ไม่นับวันหยุดตามปฏิทินส่วนกลาง) → แจ้งเตือนผู้อนุมัติหลักซ้ำ และเปิดสิทธิ์ให้ backup_approvers ดำเนินการได้ FR-22หมดอายุ: คำขอยังไม่มีผลเมื่อเหลือ 24 ชม. ก่อนเวลาเริ่ม → สถานะ "หมดอายุ" ปลดช่วงถือครอง แจ้งผู้จองและผู้อนุมัติ FR-23คำขอเร่งด่วน = คำขอในห้องต้องอนุมัติที่เวลาเริ่มห่างจากเวลาส่งน้อยกว่า SLA + 24 ชม. (ค่าเริ่มต้น: น้อยกว่า 2 วันทำการ + 24 ชม.) ระบบเตือนผู้จองว่า "อาจไม่ทันอนุมัติ" ไม่บล็อกการส่ง และส่งให้ผู้อนุมัติหลักและ backup_approvers พร้อมกันทันที โดยทุกคนดำเนินการได้โดยไม่ต้องรอ SLA เพื่อปิดช่องว่างที่คำขอหมดอายุก่อนสิทธิ์ผู้อนุมัติสำรองจะเปิด · คำขอที่ส่งล่วงหน้าน้อยกว่า 24 ชม. หมดอายุเมื่อถึงเวลาเริ่มแทนเกณฑ์ FR-22 FR-24การปฏิเสธต้องระบุเหตุผล ระบบแสดงเหตุผลแก่ผู้จอง

8. การบังคับย้าย (Preemption)

ใช้เมื่อกิจกรรมที่มีลำดับความสำคัญสูงกว่าต้องใช้ห้องที่มีการจองอนุมัติแล้ว เป็นกระบวนการแยก ไม่ใช่การลบหรือแก้ไขการจองเดิม

FR-25ผู้สั่งได้: ผู้ดูแลระบบ และผู้อนุมัติหลัก (หรือผู้รักษาการ) ของห้องนั้น ต้องกรอก เหตุผล เลขอ้างอิงคำสั่ง/หนังสือ และระบุการจองใหม่ที่จะเข้าแทน FR-26ระบบเสนอห้องและเวลาทดแทนที่ว่างและความจุพอ อย่างน้อย 3 ตัวเลือก (ถ้ามี) โดยเรียงลำดับ (1) ห้องนโยบายอัตโนมัติ (2) ห้องที่ผู้สั่งมีสิทธิ์อนุมัติ (3) ห้องอื่น ผู้สั่งเลือกหนึ่งหรือระบุว่า "ไม่มีทดแทน" · ห้องทดแทนในกลุ่ม (1)–(2) สร้างเป็นสถานะ "อนุมัติ" ทันที · ห้องทดแทนในกลุ่ม (3) สร้างเป็น "รออนุมัติ" แบบเร่งด่วน (FR-23) ส่งผู้อนุมัติของห้องนั้น และแจ้งผู้จองเดิมว่า "ห้องทดแทนยังรออนุมัติ" ผู้สั่งย้ายไม่มีสิทธิ์อนุมัติแทนเจ้าของห้องทดแทน FR-27การบังคับย้ายทำใน transaction เดียว ตามลำดับ: (1) ตั้ง released_at ให้แถวถือครองทั้งหมดของการจองเดิม และเปลี่ยนสถานะการใช้งานเป็น "ถูกย้าย" (สถานะคำขอคง "อนุมัติ" เพื่อรักษาประวัติ แต่ไม่ถือครองเวลาอีก) (2) สร้างการจองที่เข้าแทนในห้องเดิม (3) สร้างการจองทดแทนให้ผู้จองเดิมตาม FR-26 ถ้ามี ทั้งสามรายการเชื่อมกันด้วย preemption_id หากขั้นใดล้มเหลวให้ย้อนกลับทั้งหมด FR-28ผู้จองเดิมได้รับแจ้งทันที ต้องกดรับทราบ ถ้าไม่ตอบใน 24 ชม. ระบบบันทึกว่า "ถือว่ารับทราบ" และแจ้งผู้สั่งย้าย FR-29ข้อความแจ้งไม่เปิดเผยชื่อกิจกรรมที่เข้าแทน ระบุเพียง "ถูกย้ายตามคำสั่ง <เลขอ้างอิง> โดย <ตำแหน่ง>" FR-30ทุกการบังคับย้ายปรากฏในรายงานแยก และผู้บังคับบัญชาดูได้

ไม่มีหน้าสมัคร อีเมลต้องลงท้าย @signalschool.ac.th (ตรวจทั้งตอนสร้างและตอนแก้ไข) ผูกหมายเลขประจำตัวกำลังพล SR-03การเปิดใช้บัญชีครั้งแรกผ่านลิงก์ที่ส่งไปยังอีเมลนั้น อายุ 72 ชม. ผู้ใช้ตั้งรหัสผ่านและ ทุกกรณีที่ระงับ ระบบแสดงรายการจองในอนาคตของบัญชีนั้นให้ผู้ดูแลระบบ โอนผู้รับผิดชอบ ไปยังผู้ใช้อื่นในหน่วยเดียวกัน หรือยกเลิกพร้อมแจ้งผู้เกี่ยวข้อง SR-05รหัสผ่านอย่างน้อย 12 ตัวอักษร ล็อกบัญชี 15 ค่าเริ่มต้นผู้ใช้ทั่วไปเห็น "ไม่ว่าง" + หน่วยที่จอง · ผู้จอง ผู้ร่วมหน่วย ผู้อนุมัติและเจ้าหน้าที่ของห้องนั้นเห็นเต็ม · ผู้จองตั้ง visibility = restricted ได้เพื่อให้ทั่วไปเห็นแค่ "ไม่ว่าง" · NF-19หน้าหลักต้องผ่าน Core Web Vitals ที่ percentile 75 ทั้งมือถือและคอมพิวเตอร์: LCP ≤ 2.5 วินาที, INP ≤ 200 มิลลิวินาที และ CLS ≤ 0.1 วัดในสภาพเครือข่ายที่กำหนดสำหรับ pilot และเก็บค่าจากการใช้งานจริงหลังเปิดระบบ NF-20ทดสอบโหลดด้วยผู้ใช้พร้อมกัน 200 รายและข้อมูลอย่างน้อย 100 ห้อง/อุปกรณ์ 10,000 การจอง โดยมีสัดส่วน อ่านปฏิทิน 70% ค้นหาห้อง 20% และสร้าง/แก้ไข/อนุมัติ 10% API อ่านมี p95 ≤ 500 มิลลิวินาที API เขียนมี p95 ≤ 1 วินาที (ไม่รวมการส่ง LINE) อัตรา HTTP 5xx ต่ำกว่า 0.1% และต้องไม่เกิดการจองซ้อน NF-21การส่ง LINE การสร้างรายงาน และงานที่ใช้เวลานานทำแบบ asynchronous ไม่บล็อกการตอบผู้ใช้ ปฏิทินโหลดเฉพาะช่วงและห้องที่ผู้ใช้กำลังดู ระบบเก็บ metric ของ latency, error rate, queue lag, job failure และ database connection พร้อมแจ้งเตือนเมื่อเกินเกณฑ์

NF-22ซอร์สโค้ดต้องผ่าน formatter, linter, type checker, static analysis และ secret scan อัตโนมัติใน CI ก่อนรวมโค้ด ห้ามมีข้อผิดพลาดระดับสูงคงค้าง ทุกการเปลี่ยนแปลงผ่าน code review อย่างน้อย 1 คนและเชื่อมโยงกับข้อกำหนดหรือรายการงาน NF-23โมดูล Booking, conflict detection, Approval และ Preemption ต้องมี branch coverage ไม่น้อยกว่า 90% โค้ด domain/application รวมไม่น้อยกว่า 80% พร้อม integration test ของฐานข้อมูลและ end-to-end test สำหรับเส้นทางหลัก Coverage ใช้เป็นเกณฑ์ขั้นต่ำและไม่แทนการตรวจคุณภาพ test case NF-24ห้ามมี circular dependency ระหว่างโมดูล กฎธุรกิจต้องไม่มีสำเนาซ้ำใน UI, API และ job ค่าที่เปลี่ยนตามหน่วยงานอยู่ใน configuration หรือทะเบียนระบบ ไม่ hard-code และห้ามเก็บ secret ในซอร์สโค้ด เอกสาร public API และเหตุผลของกฎที่ซับซ้อนต้องอยู่ใกล้โค้ดที่เกี่ยวข้อง NF-25ทุก release ต้องสร้าง artifact แบบทำซ้ำได้ มีเลขรุ่น release note database migration แผน rollback และผลทดสอบอัตโนมัติ สามารถย้อนกลับรุ่นแอปพลิเคชันภายใน 30 นาทีโดยไม่สูญเสียการจองที่ยืนยันแล้ว — เงื่อนไขคือ migration ของรุ่นนั้นเป็นแบบ expand/contract ตาม NF-17 (rollback แอปพลิเคชันอย่างเดียว ไม่ย้อน schema) release ที่มีขั้น contract ต้องระบุใน release note ว่า rollback ได้ถึงรุ่นใด · ต้องทดสอบ rollback อย่างน้อยหนึ่งครั้งก่อนเปิด pilot

15.2 เกณฑ์รับมอบระยะที่ 1

  1. ไม่มีการจองซ้อนทับเกิดขึ้นตลอด pilot (ตรวจจากฐานข้อมูล)
  2. ทุกคำขอในห้องต้องอนุมัติได้ผลภายในเส้นตาย หรือหมดอายุอย่างถูกต้อง ไม่มีคำขอค้างไร้สถานะ
  3. ทดสอบสถานการณ์: ผู้อนุมัติลา → ผู้รักษาการอนุมัติได้ และ log แสดง on_behalf_of
  4. ทดสอบบังคับย้ายอย่างน้อย 2 ครั้ง (ห้องทดแทนที่ผู้สั่งมีสิทธิ์ และห้องทดแทนต่างเจ้าของ) ครบตาม FR-25–30 และยืนยันว่าช่วงเวลาเดิมว่างให้การจองที่เข้าแทนได้ทันที
  5. ทดสอบ amendment ตาม FR-34–38 อย่างน้อย 3 กรณี: (ก) เพิ่มบุคคลภายนอกในห้องอัตโนมัติ → amendment เข้า "รออนุมัติ" การจองเดิมยังถือครองช่วงเดิม (ข) ผู้อนุมัติ ปฏิเสธ amendment → การจองเดิมไม่เปลี่ยนและช่วงใหม่ว่างให้ผู้อื่น (ค) ย้ายห้องข้ามเจ้าของแล้วอนุมัติ → ช่วงเดิมถูกปลดและช่วงใหม่เป็นหลักใน transaction เดียว · ยืนยันว่ายื่น amendment ซ้อนรายการที่รออยู่ไม่ได้ (FR-36)
  6. ทดสอบคำขอเร่งด่วนที่ส่งล่วงหน้า 30 ชม. → ผู้อนุมัติสำรองดำเนินการได้ทันทีตาม FR-23
  7. ทดสอบจองชุดที่ชนบางครั้ง ผู้ใช้เลือก "เฉพาะครั้งที่ว่าง" ได้ถูกต้อง
  8. ห้องงดใช้ → ผู้จองที่ได้รับผลกระทบได้รับแจ้งทุกราย
  9. ผู้ใช้ทั่วไปไม่เห็นชื่อกิจกรรมที่ตั้ง visibility จำกัด (ทดสอบด้วยบัญชีต่างหน่วย)
  10. ข้อความ LINE ไม่มีชื่อกิจกรรม (ตรวจ log การส่งทั้งหมด)
  11. ทดสอบกู้คืนจากสำรองข้อมูลสำเร็จ 1 ครั้ง
  12. ผ่านการตรวจสอบความปลอดภัยจากหน่วยก่อนเปิดอินเทอร์เน็ต (SR-01–18) รวม ASVS mapping ผลสแกนช่องโหว่ และรายงานทดสอบเจาะระบบ โดยไม่มี Critical/High คงค้าง
  13. ผ่านการตรวจ WCAG 2.2 ระดับ AA ทั้งอัตโนมัติและทดสอบด้วยแป้นพิมพ์/โปรแกรมอ่านหน้าจอในฟังก์ชันหลักตาม NF-10–12 โดยไม่มีข้อบกพร่องระดับ A หรือ AA คงค้าง
  14. ผ่าน usability test ตาม NF-13 (SUS ≥ 75 เป็นเกณฑ์คุณภาพหลัก) และแบบสอบถามผู้ใช้หลัง pilot มีความพึงพอใจเฉลี่ย ≥ 3.5 / 5 ตามข้อตกลง 0.1 — เป้าหมาย ≥ 4.0 / 5 ใช้หลังขยายทั้งโรงเรียน
  15. ผ่าน architecture review ตาม NF-15–18 เอกสาร C4, ER, sequence, OpenAPI และ ADR ตรงกับระบบที่ส่งมอบ
  16. ผ่าน Core Web Vitals และ load test ตาม NF-19–21 พร้อมรายงาน p75/p95, error rate และผลตรวจว่าไม่มีการจองซ้อน
  17. CI ผ่าน quality gate และ automated test ตาม NF-22–24 พร้อมสาธิต deployment และ rollback ตาม NF-25
